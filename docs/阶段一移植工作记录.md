## 4. Linux kernel 和设备描述

### 4.1 Kernel 来源和固定版本

新增 [`layers/meta-balena-rockpi/recipes-kernel/linux/linux-seeed-rk3588_6.1.bb`](../layers/meta-balena-rockpi/recipes-kernel/linux/linux-seeed-rk3588_6.1.bb)，kernel 来源为：

| 项目  | 内容                                                                    |
| --- | --------------------------------------------------------------------- |
| 仓库  | [`armbian/linux-rockchip`](https://github.com/armbian/linux-rockchip) |
| 分支  | `rk-6.1-rkr5.1`                                                       |
| 提交  | `c6157104418d012823413c02f9222f3fe123dd25`                            |
| 版本  | Linux 6.1 vendor kernel                                               |

选择该提交的原因是它已经包含 Seeed reComputer RK3588 DevKit 的板级 DTS、摄像头 include 文件以及对应的 kernel `Makefile` 条目：

- `rk3588-recomputer-rk3588-devkit.dts`；
- `recomputer-rk3588-devkit-cam.dtsi`；
- 对应的设备树编译入口。

配方同时引入 [`balena-rk3588.cfg`](../layers/meta-balena-rockpi/recipes-kernel/linux/files/balena-rk3588.cfg)，补充 Balena 最小启动所需的 Rockchip、串口、MMC、NVMe、EXT4、devtmpfs、网络和 USB 相关配置。

### 4.2 Kernel 侧主要设置

配方中固定了以下关键变量：

- `COMPATIBLE_MACHINE = "^recomputer-rk3588-devkit$"`；
- `KBRANCH = "rk-6.1-rkr5.1"`；
- `SRCREV = "c6157104418d012823413c02f9222f3fe123dd25"`；
- `KERNEL_IMAGETYPE = "Image"`；
- `KERNEL_DEVICETREE = "rockchip/rk3588-recomputer-rk3588-devkit.dtb"`；
- 通过 `inherit kernel-yocto` 和 `SRC_URI` 接入 Balena 配置片段。

这样处理后，板级 Linux DTS 来自固定的远程 kernel 提交，不依赖本地 Armbian 工作树中的未提交修改。

当前配置片段额外启用 `CONFIG_ARM_ROCKCHIP_CPUFREQ=y`；最终 `.config` 已确认包含 `CONFIG_ARCH_ROCKCHIP=y`、`CONFIG_CPUFREQ_DT=y` 和 `CONFIG_ARM_ROCKCHIP_CPUFREQ=y`。由于 vendor kernel 源码报告为 `6.1.115`，而配方 PV 保持稳定的 `6.1+git`，配方设置 `KERNEL_VERSION_SANITY_SKIP = "1"`，避免版本 sanity check 将源码 patchlevel 与配方 PV 的差异误判为错误。

## 5. U-Boot 和板级文件

### 5.1 U-Boot 来源

RK3588 的 U-Boot 配置通过 [`u-boot_%.bbappend`](../layers/meta-balena-rockpi/recipes-bsp/u-boot/u-boot_%25.bbappend) 选择：

| 项目  | 内容                                                |
| --- | ------------------------------------------------- |
| 仓库  | [`radxa/u-boot`](https://github.com/radxa/u-boot) |
| 分支  | `next-dev-v2024.10`                               |
| 提交  | `39cd993e5d6296635438e84f4576b3a9bf76f86e`        |

该提交提供 RK3588 的 Radxa U-Boot 基础，但本身不包含 Seeed reComputer RK3588 DevKit 的板级 defconfig 和 DTS。因此本阶段采用显式 layer 输入的过渡方案：

1. 将板级 U-Boot 文件放入 `meta-balena-rockpi`；
2. 在 `do_configure:prepend` 阶段将它们安装到 U-Boot 源码树；
3. 继续使用固定的 Radxa U-Boot 提交作为源码基础。

这使当前配置可以继续推进，但后续最好将板级差异整理成可审查、可维护的 Yocto patch，或使用已经包含这些文件的稳定上游提交。

U-Boot 配置中的默认设备树为 `rk3588-recomputer-rk3588-devkit`，与 `UBOOT_MACHINE` 和 flasher 中的 DTB 文件名保持一致。

Radxa vendor tree 的标准 `all` 目标只生成 `u-boot.bin`、SPL 和 TPL，而本板 Rockchip 启动链需要 `u-boot.itb` 与 `idbloader.img`。因此 `u-boot_%.bbappend` 的 `do_compile:append:recomputer-rk3588-devkit` 会在 `${B}` 中链接 FIT 生成器脚本，使用固定的 `BL31` 生成 `u-boot.its`/`u-boot.itb`，再用 `u-boot-tpl.bin`、`u-boot-spl.bin` 和 `mkimage -T rksd` 生成 `idbloader.img`。该 hook 已由 BitBake `do_compile` 重新执行验证通过。

## 6. 镜像、GPT 和启动链布局

### 6.1 裸盘启动偏移

RK3588 Rockchip loader 不从普通文件系统分区的起始位置启动，而是写入固定裸盘偏移。当前配置使用 512 字节扇区：

| 内容              | 起始扇区    | 起始字节偏移   | 说明                     |
| --------------- | -------:| --------:| ---------------------- |
| `idbloader.img` | `64`    | `32 KiB` | Rockchip SPL/DDR 初始化镜像 |
| `u-boot.itb`    | `16384` | `8 MiB`  | U-Boot proper/FIT 镜像   |

### 6.2 镜像配方修改

涉及三个镜像文件：

- [`layers/meta-balena-rockpi/recipes-core/images/balena-image.inc`](../layers/meta-balena-rockpi/recipes-core/images/balena-image.inc)
  - 设置 RK3588 使用 GPT；
  - 创建 `loader1` 和 `loader2` 两个 loader 区域；
  - 在 `balenaos-img` 生成阶段使用 `dd` 将 `idbloader.img` 写入扇区 64，将 `u-boot.itb` 写入扇区 16384；
  - 设置 RK3588 的 rootfs、boot 和 state 空间大小。
- [`layers/meta-balena-rockpi/recipes-core/images/balena-image.bbappend`](../layers/meta-balena-rockpi/recipes-core/images/balena-image.bbappend)
  - 将 `idbloader.img` 和 `u-boot.itb` 放入 Balena boot 分区可见的文件集合；
  - 为内部镜像加入 `u-boot-extlinux`。
- [`layers/meta-balena-rockpi/recipes-core/images/balena-image-flasher.bbappend`](../layers/meta-balena-rockpi/recipes-core/images/balena-image-flasher.bbappend)
  - 将 flasher 的 `extlinux.conf`、RK3588 DTB 和 initramfs kernel 放入 boot 分区；
  - 为未压缩的 `Image` 预留更大的 boot 分区。

当前预期的 GPT 顺序为：

1. `loader1`；
2. `loader2`；
3. Balena boot；
4. Balena root A；
5. 其他 Balena state/root 分区。

因此当前 machine 的启动变量为：

- `BALENA_BOOT_PART = "3"`；
- `BALENA_DEFAULT_ROOT_PART = "4"`。

分区编号是根据当前 raw-loader 布局推导的配置，必须在第一次 BitBake/WIC 构建后从实际分区表和启动日志复核，不能仅凭静态配置视为已验证。

### 8.2 完整镜像构建结果

在管理员临时允许 user namespace、并确认 `docker info` 成功后，执行了完整构建：

```text
MACHINE=recomputer-rk3588-devkit
BALENA_API_VERSION=1.44
GOPROXY=direct
BB_NUMBER_THREADS=4
PARALLEL_MAKE=-j4
bitbake balena-image-flasher
```

首次完整构建在 `docker-disk:do_compile` 失败。失败原因不是宿主 Docker daemon，而是 docker-disk 容器内启动的 Docker 19.03 daemon 无法创建 legacy iptables NAT 链：

```text
failed to create NAT chain DOCKER
iptables ... Table does not exist
```

docker-disk 内层 daemon 只用于拉取 Supervisor 镜像和生成 `resin-data.img`，不需要容器网络转发。因此新增：

- [`layers/meta-balena-rockpi/recipes-containers/docker-disk/docker-disk.bbappend`](../layers/meta-balena-rockpi/recipes-containers/docker-disk/docker-disk.bbappend)

该 bbappend 在 `do_compile` 前将内层 `dockerd` 命令增加 `--iptables=false`。单独执行 `bitbake -c clean docker-disk` 和 `bitbake -c compile docker-disk` 已通过，随后完整构建重新执行成功。

完整构建最终结果：`6041` 个任务全部成功，只有主机发行版、配方 `S` 路径和少量构建环境相关 warning，没有 Error。为避免独立 BitBake 任务间的时间戳变化导致 license manifest 名称不一致，强制重建 `balena-image:do_rootfs` 后，最终构建固定使用：

```text
IMAGE_VERSION_SUFFIX=-20260824064709
```

最终 flasher 产物：

```text
build/tmp/deploy/images/recomputer-rk3588-devkit/
└── balena-image-flasher-recomputer-rk3588-devkit-20260824064709.balenaos-img
```

产物大小为 `3,238,002,688` bytes（约 3.02 GiB），SHA-256 为：

```text
c8d6470d546f73beecf984a8462877722639782613a9c026d6fdc155ea82495e
```

同目录同时生成了 `.bmap`、`.ext4`、rootfs license manifest、SPDX/testdata 文件，以及用于板级启动的 `Image`、RK3588 DTB、`extlinux.conf`、`idbloader.img` 和 `u-boot.itb`。

### 8.2.1 本轮构建问题及处理

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| `libcap-ng:do_patch` 属主/权限错误 | Docker 构建和宿主工作树混用后，部分工作目录文件属主不一致 | 清理并重新执行该配方任务；未修改上游配方 |
| `time-native` 在 GCC 15/glibc 下编译失败 | 旧源码使用的 signal handler 类型与现代头文件声明不兼容 | 增加 `recipes-extended/time/time_%.bbappend` 和 signal handler patch |
| RK3588 kernel 带入大量无关平台驱动 | 通用 vendor `defconfig` 启用了非 Rockchip 图形/SoC 驱动 | 切换到 `rockchip_linux_defconfig`，并在 `balena-rk3588.cfg` 中禁用 `CONFIG_DRM_V3D` |
| `balena-supervisor:do_install` 找不到设备 JSON | CoffeeScript 已存在，但对应 JSON 尚未生成 | 执行 `build-device-type-json.sh` 生成设备类型 JSON |
| `kernel-headers-test` 访问 Docker API 失败 | Docker 29 daemon 要求 API 至少为 1.44，而 meta-balena 默认使用 1.41 | 构建环境设置 `BALENA_API_VERSION=1.44`，未修改上游 meta-balena |
| `mobynit` 下载 `golang.org/x/sys` 返回 EOF | `proxy.golang.org` 下载链路临时中断 | 构建环境设置 `GOPROXY=direct` 重试 |
| U-Boot license checksum 不匹配 | Radxa vendor tree 的 `Licenses/README` 与 Poky 2024.01 配方记录不同 | 增加 machine 专属 `LIC_FILES_CHKSUM`，当前 md5 为 `a2c678cfd4a4d97135585cad908541c6` |
| `docker-disk:do_compile` 内层 Docker daemon 创建 NAT 链失败 | Docker 19.03 DinD 默认初始化 iptables，当前容器环境没有 legacy NAT 表 | 本 layer 的 `docker-disk.bbappend` 在内层 `dockerd` 增加 `--iptables=false`；单任务和完整构建均通过 |
| `do_image_complete` 找不到 license manifest | 分开启动 BitBake 时 `IMAGE_NAME` 的 DATETIME 变化，而缓存 rootfs manifest 使用上一时间戳 | 强制重建 `balena-image:do_rootfs`，最终构建固定 `IMAGE_VERSION_SUFFIX` 与 manifest 时间戳 |

上述问题中，`BALENA_API_VERSION`、`GOPROXY`、固定镜像时间戳属于本次构建环境参数；`time-native`、kernel 配置、docker-disk bbappend 和 U-Boot checksum 属于仓库内的可复现修改。

### 8.3 最终镜像布局静态验证

对最终 flasher `.balenaos-img` 使用 `parted`/`fdisk` 进行只读检查，实际 GPT 为：

| 分区 | 起始扇区 | 结束扇区 | 大小 | 名称 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 64 | 8063 | 8000 sectors | `loader1` |
| 2 | 16384 | 24575 | 8192 sectors | `loader2` |
| 3 | 81920 | 409599 | 327680 sectors / 160 MiB | `flash-boot` |
| 4 | 409600 | 6275071 | 5865472 sectors | `flash-rootA` |
| 5 | 6275072 | 6283263 | 8192 sectors | `flash-rootB` |
| 6 | 6283264 | 6291455 | 8192 sectors | `flash-state` |
| 7 | 6291456 | 6322175 | 30720 sectors | `flash-data` |

这与 machine/U-Boot 配置中的 `BALENA_BOOT_PART=3`、`BALENA_DEFAULT_ROOT_PART=4` 以及 raw-loader 偏移一致：

- `idbloader.img` 写入 sector 64（32 KiB）；
- `u-boot.itb` 写入 sector 16384（8 MiB）；
- boot 分区从 sector 81920 开始，包含 extlinux、Image 和 RK3588 DTB。

内部 `balena-image` 的 `extlinux.conf` 使用 `/boot/Image` 和 `/boot/rk3588-recomputer-rk3588-devkit.dtb`；flasher 专用 `extlinux.conf_flasher` 使用 `/Image` 和 `/rk3588-recomputer-rk3588-devkit.dtb`，两者控制台均为 `ttyS2,1500000n8`。设备 JSON 已生成并指定 flasher 的第 3 分区 `/config.json` 配置入口。以上是镜像文件和分区布局的静态验证，尚不等同于真实板卡启动验证。

另外完成了两项内容一致性检查：

- 从最终 `.balenaos-img` 的 sector 64 提取的 loader1 与 `idbloader.img` 逐字节一致；
- 从 sector 16384 提取的 loader2 与 `u-boot.itb` 逐字节一致。

`dumpimage -l u-boot.itb` 显示 FIT 包含 U-Boot、3 段 ATF/BL31、RK3588 DevKit U-Boot DTB，并将 `rk3588-recomputer-rk3588-devkit` 设为默认配置。最终关键文件大小为：`Image` 39,668,224 bytes、板级 DTB 283,138 bytes、`idbloader.img` 251,904 bytes、`u-boot.itb` 1,713,152 bytes。

内核 Git 仓库首次完整 mirror 接收约 3.1 GiB。此前一次下载在约 1.1 GiB 处因 GitHub 连接中断，出现 `GnuTLS recv error (-110)`、`early EOF` 和无效 pack；没有继续使用损坏的临时镜像，而是在授权构建环境中重新执行 fetch。由于固定提交恰好是远程分支 tip，构建命令临时设置了 `BB_GIT_SHALLOW=1`、`BB_GIT_SHALLOW_DEPTH=1`，但 BitBake 的共享 bare mirror 阶段仍接收了较大的远程对象包。

这些结果已经证明 kernel/U-Boot、Balena flasher 镜像及其 RK3588 GPT 启动布局可以在当前构建环境中编译和打包，但不能替代真实硬件启动验证。

## 9. 当前问题和限制

### 9.1 构建环境和临时工具

- 已按根目录 [`.gitmodules`](../.gitmodules) 将 `poky`、`meta-balena`、`meta-rockchip`、`meta-openembedded`、`meta-arm`、`balena-yocto-scripts` 和 `contracts` 浅克隆到工作区；由于根目录 `.git` 仍不是完整 Git 仓库，这些目录是独立 clone，不是通过 `git submodule update` 建立的正式 superproject 状态；
- `bitbake` 已可从 `layers/poky/bitbake/bin` 启动；当前主机没有系统安装的 `chrpath`，本阶段使用解压到 `/tmp/rk-balena-tools` 的临时工具；
- 当前主机没有 `en_US.UTF-8` locale，本阶段在 `/tmp/rk-balena-locale` 生成了临时 locale 供 BitBake 使用，未修改系统 locale；
- 当前主机使用 GCC/G++ 15.2，而 Balena Scarthgap 固定的 `rust-llvm-native 1.62.0` 携带 LLVM 13。GCC 15 不再保证通过传递 include 提供旧 LLVM 所使用的定长整数类型声明，因此首次编译在 `SmallVector.h`、AMDGPU 和 X86 target description 处失败；已在 `meta-balena-rockpi` 中加入 3 个上游 LLVM backport：`0036-Add-cstdint-to-SmallVector-101761.patch`、`0037-Include-cstdint-in-AMDGPUMCTargetDesc-101766.patch` 和 `0038-Add-missing-include-to-X86MCTargetDesc.h-123320.patch`。强制重编译已通过，说明当前 GCC 15 主机可以构建该 native LLVM；这些补丁只针对旧 LLVM 的主机兼容性，不改变目标 RK3588 固件行为；
- 原生 BitBake 曾被 Ubuntu/AppArmor 的 user namespace 限制阻止：`/proc/sys/kernel/apparmor_restrict_unprivileged_userns=1`，普通用户无法完成 `uid_map` 写入；管理员已在当前构建机临时设置 `kernel.apparmor_restrict_unprivileged_userns=0`，因此 kernel/U-Boot 任务现已可以运行；
- 当前主机的发行版被识别为 `ubuntu-26.04`，不在该 Scarthgap 构建系统的已验证发行版列表中，目前仅作为临时构建环境使用；
- Docker daemon socket `/var/run/docker.sock` 在本轮构建前曾因权限不足导致 `docker-disk.bb` 主机检查失败；管理员恢复权限后，`docker info` 已成功，完整构建已完成。为避免把临时 workaround 固化进工程，临时 `BBMASK` 已从 `build/conf/local.conf` 移除，临时 `build/conf/auto.conf` 也已删除；后续构建仍需保持当前用户对 Docker socket 的访问权限；
- 已执行过一次临时移除 `create-spdx` 的 standalone deploy 任务图尝试，但仍会展开大量 native 任务；临时 `build/conf/auto.conf` 已删除，没有保留该 workaround；
- 完整 `balena-image-flasher` 构建和 GPT 镜像生成已完成；硬件首启、真实分区内容读取、hostapp 更新和断电恢复测试仍未执行。

### 9.2 U-Boot 板级文件仍是过渡集成

Radxa U-Boot 固定提交不包含 Seeed 板级文件，当前通过 layer 文件在 `do_configure` 阶段注入。该方式便于锁定文件内容并继续推进移植；完整 U-Boot 编译和 `u-boot.itb`/`idbloader.img` 生成已通过，但板级差异还没有整理为标准 Yocto patch，仍需在真实硬件上验证。

Poky 默认 U-Boot CVE backport 集合与 Radxa vendor tree 不匹配；当前仅对该 machine 移除了 10 个无法应用的 CVE patch。后续应切换到包含对应修复的 vendor 提交，或逐项把安全修复移植到 Radxa tree，不能长期把该例外视为安全结论。

### 9.3 启动布局尚未经过硬件复核

当前 `loader1`、`loader2`、boot/root 分区的顺序，以及 `BALENA_BOOT_PART=3`、`BALENA_DEFAULT_ROOT_PART=4`，已经在最终 flasher GPT 中静态确认，但仍需在真实板卡上检查：

- SD/eMMC 实际启动介质上的 GPT 分区是否被 bootrom/U-Boot 正确识别；
- `idbloader.img` 和 `u-boot.itb` 是否存在且大小合理；
- U-Boot FIT 是否包含非空、匹配的 RK3588 DTB；
- flasher 中的 `extlinux.conf`、kernel 和 DTB 路径是否一致；
- 实际 SD/eMMC 启动是否能到达 BalenaOS userspace；
- 第 3 分区 `/config.json` 写入和 Supervisor 初始化是否正常。

### 9.4 尚未纳入的功能

以下功能不在当前最小启动骨架中，后续需要逐项接入和验证：

- Panthor/Mesa 图形栈；
- AIC8800 Wi-Fi/蓝牙固件和驱动；
- 摄像头及完整 camera pipeline；
- Armbian 专属 OTA 或其他 vendor 扩展。

### 9.5 Git 工作区限制

当前工作区根目录的 `.git` 不是可正常操作的完整 Git 仓库，`git status` 返回“not a git repository”，因此本阶段无法在此环境中创建或确认 Git commit。文件修改仍保存在工作区，需要在完整仓库环境中重新检查差异并提交。
